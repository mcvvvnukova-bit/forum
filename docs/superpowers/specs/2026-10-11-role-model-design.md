# Ролевая модель IAM — PROJ-171

Основание: поручение реализовать ролевую модель и назначить пользователя с телефоном `+79010000001` администратором системы; опубликованная [IAM.01.02](https://docs.astforum.ru/doc/iam0102-rolevaya-model-VbZ7MBWv2A). [PROJ-171](https://roadmap.astforum.ru/work_packages/PROJ-171) относится к [PROJ-40](https://roadmap.astforum.ru/work_packages/PROJ-40) и [PROJ-45](https://roadmap.astforum.ru/work_packages/PROJ-45).

## Решение

Использовать фиксированный каталог шести ролей и серверную проверку разрешений в явной области. Расширить существующий IAM аддитивно: действующие business grants `provider`/`customer` и настройка личного исполнителя сохраняются как отдельные бизнес-признаки. Новые IAM-назначения не смешиваются с этими grants. Общий `users`/`persons` не зависит от наличия участника-исполнителя. Личный контекст имеет ключ `person:{userId}` и nullable `participantId`, корпоративный — `organization:{organizationId}`, служебный — `platform`.

Один глобальный флаг admin недостаточен для изоляции организаций. Универсальный конструктор произвольных ролей избыточен для согласованного фиксированного каталога. Поэтому выбран каталог разрешений в коде, отдельные назначения в PostgreSQL и независимая проверка членства/полномочий.

## Роли и разрешения

| Роль | Область | Разрешения |
| --- | --- | --- |
| individual | Собственный личный контекст | personal.profile.read, personal.profile.update, personal.business.use, organization.add |
| organization_employee | Одна компания | organization.business.read, organization.business.draft; только объекты, доступные по правилам бизнес-модуля |
| organization_admin | Одна компания | employee-разрешения, organization.business.publish, organization.profile.update, organization.verification.manage, organization.members.manage, organization.audit.read |
| organization_signer | Одна компания | employee-разрешения; organization.documents.sign требует отдельного действующего подтверждения и проверки области конкретного документа |
| platform_moderator | Платформа | platform.moderation.review, platform.restrictions.manage, platform.audit.read; аудит ограничен собственными служебными решениями |
| platform_admin | Платформа | moderator-разрешения, platform.roles.manage; служебный аудит целиком |

Роль platform_admin не обходит корпоративное членство и не даёт имперсонацию или право подписи. Блокировка пользователя, отзыв членства, недопустимый статус организации и истечение основания имеют приоритет над ролью. Неизвестный permission запрещён. Личные права действуют без создания company или business participant.

## Хранение и миграция

`008_iam_roles` добавляет `users.access_version`, версии членств, `iam_role_assignments`, журнал идемпотентности. Корпоративное назначение связано с тем же `(user_id, organization_id)` членством FK; служебное имеет null scope_id. Области, роли, статусы, сроки, неизменяемость владельца и уникальность защищены БД. Каталог версионируется исходным кодом. Активные подтверждённые legacy-членства переносятся как employee; legacy admin переносится только с действующим подтверждённым administrator-основанием. Неподтверждённый legacy admin не становится действующим администратором.

Для signer существующая таблица organization_authorities получает отдельный тип signer и проверяемую область allowed_actions. API не принимает от клиента утверждение о подтверждённом основании. Без подтверждения подпись запрещена. Начальное назначение администратора компании через Диадок и получение КЭП/МЧД выполняются своими интеграционными фичами; эта реализация потребляет их подтверждённые результаты и не заменяет доказательства ручными флагами.

Миграция аддитивная. Откат приложения сохраняет новые данные; для удаления схемы используется отдельная проверенная rollback-процедура на изолированной БД, которая отказывается удалять действующие назначения/аудит. Runtime получает только явные необходимые grants; никаких глобальных default privileges или SECURITY DEFINER обходов.

## Серверный контракт

Сессия сохраняет совместимые `user`, `participant`, `roles`, `expiresAt` и добавляет `platformRoles`, `accessVersion`, `csrfToken`. Данные сессии и права всегда читаются из БД, без доверия к клиентским roles и без длительного кеша. Личный базовый individual не снимается ролью компании или платформы.

* `GET /api/iam/roles` — фиксированный каталог для вошедшего пользователя.
* `GET /api/iam/contexts?cursor=&limit=` — собственные контексты с ролями, permissions, nullable participantId и accessVersion; cursor связан с пользователем, limit 25/100.
* `POST /api/iam/context/resolve` с `{contextKey}` — проверяет выбранный контекст, не меняет общую сессию.
* `GET /api/iam/platform-users?cursor=&limit=` — минимальные данные существующих идентифицированных пользователей и их служебные назначения, только platform.roles.manage.
* `POST /api/iam/platform-role-assignments` с `{targetUserId,roleCode,reason}` — назначает только platform_admin/platform_moderator активному идентифицированному пользователю.
* `PATCH /api/iam/platform-role-assignments/{id}` с `{status,reason}` — меняет только active/revoked существующего назначения.
* `GET /api/iam/organizations/{id}/members` — активному organization_admin своей компании.
* `PATCH /api/iam/organizations/{id}/members/{membershipId}` с `{roles,status,reason}` — действующему organization_admin; роли только corporate, членство уже существует. Новое членство, принятие приглашения и внешняя верификация принадлежат отдельным фичам.
* `GET /api/iam/audit-events?cursor=&limit=` — служебный аудит; администратор читает все служебные решения, модератор только свои.

Защищённые IAM-запросы содержат `X-Forum-Context`. Изменяющие запросы также требуют правильный Origin, `X-Forum-CSRF` из серверной сессии, Idempotency-Key; изменение существующей записи требует If-Match вида `"1"`. Повтор ключа с тем же телом возвращает прежний результат, с другим — 409. Повтор после потери доступа не возвращает закрытые данные. Записи идемпотентности сохраняются минимум 24 часа.

Автор берётся только из сессии. Проверка доступа, изменение, рост версии и аудит атомарны. Изменение служебных ролей сериализуется платформенной блокировкой; корпоративных — блокировкой компании. Нельзя снять последнего действующего admin, включая параллельные запросы. Security-блокировка человека не сохраняет доступ ради этого правила. Отозванные права перестают действовать после коммита для следующего запроса, в том числе с прежней cookie.

Ошибки: 400 invalid_request/context_required; 401 unauthenticated; 403 forbidden/invalid_origin/invalid_csrf; 404 not_found для недоступного объекта; 409 idempotency_conflict/last_admin; 412 stale_version; 503 temporarily_unavailable при недоступной обязательной проверке. Ответы Cache-Control: no-store, без токенов, provider claims и приватных профилей других людей.

## Первый системный администратор

Однократная owner-процедура сначала нормализует указанный телефон, требует единственное совпадение активного пользователя с подтверждённой Sber-идентичностью и проверяет ожидаемый userId. Назначение хранится по userId, без whitelist номера при каждом входе. Если совпадений нет или несколько, процедура завершается без изменений. Повтор для уже назначенного пользователя идемпотентен; существующего другого администратора процедура не обходит. Назначение и аудит выполняются в одной транзакции.

Проверка 11.10.2026: действующий API имеет PUBLIC_ORIGIN `https://dev.astforum.ru`, использует БД `forum.public`, миграции 001–007. Для номера найден один активный Sber-пользователь `01a1186d-aecb-731f-9301-d9bc27807e1e`. Это снимок перед реализацией: перед назначением процедура обязана повторить проверки. Production-публикация не входит в это поручение.

## Интерфейс и приёмка

Служебный раздел показывается только с platform-admin полномочиями из серверной сессии и повторно проверяет доступ на сервере при загрузке. Он показывает служебные роли и позволяет назначать/отзывать их с обязательной причиной. Корпоративное управление показывает роли только доступной компании; базовые бизнес-признаки не подменяют роли. Всё на существующих Primer-композициях и Light-токенах. Клавиатура, loading/error/empty/403/401/stale states, предотвращение повторной отправки, ширины 320/390/768/1440.

Приёмка: гостевой отказ; ordinary user не может назначить себе роль; admin назначает moderator; moderator не назначает admin; platform_admin не получает company-доступ; смена organization ID и чужой membership ID не открывают данные; signer без подтверждения не подписывает; отзыв виден со старой cookie; idempotency и If-Match работают; два одновременных снятия не удаляют всех admin; аудитная ошибка откатывает grant; phone bootstrap не создаёт аккаунт, не допускает неоднозначность и не переносит права при смене номера. PostgreSQL-тесты, web-тесты, сборки/типы/линтер, Primer-проверка, браузерная проверка. Все коммиты — PROJ-171, GitHub PR содержит OP#PROJ-171, OP#PROJ-40 и OP#PROJ-45, связь проверяется в OpenProject.
