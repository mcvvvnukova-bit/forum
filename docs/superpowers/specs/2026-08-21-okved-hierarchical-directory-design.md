# Иерархический справочник строительных ОКВЭД

## Цель

Добавить в PostgreSQL отдельный иерархический справочник выбранных строительных ОКВЭД и связать его с таблицей `company_okveds`. Справочник должен хранить восстановленные полные коды и по одному значению каждого из трёх аналитических измерений.

Источник требований — задача [«Определить аналитику по ОКВЭД»](codex://threads/01a024bf-2f29-7bd1-b5d5-62b81ce36329). В исходной выборке 967 строк строительной экосистемы; числовое форматирование породило коллизии наподобие `16.1` и `16.10`, поэтому коды нельзя импортировать как числа.

## Границы изменения

В ER-диаграмму добавляются четыре таблицы:

1. `okveds` — иерархический справочник выбранных строительных ОКВЭД.
2. `business_segments` — бизнес-сегменты.
3. `commercial_roles` — коммерческие роли.
4. `offer_types` — типы предмета предложения.

Таблица `company_okveds` сохраняет текущую структуру, но поле `code` становится одновременно первичным и внешним ключом: `PK,FK`.

Импорт данных, наполнение бизнес-сегментов и присвоение аналитических значений конкретным кодам не входят в изменение FigJam. Диаграмма фиксирует целевую структуру БД и ограничения.

## Таблица `okveds`

| Тип ключа | Поле | Тип данных | Ограничение |
|---|---|---|---|
| PK | `code` | `varchar(8)` | полный канонический код в текстовом формате |
| FK | `parent_code` | `varchar(8)` | nullable, ссылка на `okveds.code` |
|  | `level` | `smallint` | уровень в иерархии |
|  | `section` | `char(1)` | раздел ОКВЭД: `C`, `F`, `G` и т. д. |
|  | `name` | `text` | официальное наименование |
| FK | `business_segment_code` | `text` | nullable |
| FK | `commercial_role_code` | `text` | nullable |
| FK | `offer_type_code` | `text` | nullable |
|  | `created_at` | `timestamptz` | время создания записи |
|  | `updated_at` | `timestamptz` | время последнего изменения |

`parent_code` задаёт иерархию через самоссылочную связь «один родитель — много дочерних кодов». Корневые записи не имеют родителя. Поле `level` хранится явно для быстрых выборок по уровню классификатора.

Три аналитических внешних ключа допускают `NULL` на этапе классификации. После присвоения в каждом измерении у кода может быть только одно значение; это обеспечивается скалярными FK-полями без связующих таблиц.

## Аналитические справочники

`business_segments`, `commercial_roles` и `offer_types` имеют одинаковую структуру:

| Тип ключа | Поле | Тип данных | Ограничение |
|---|---|---|---|
| PK | `code` | `text` | стабильный машинный код |
| UK | `name` | `text` | уникальное отображаемое название |
|  | `description` | `text` | определение значения |
|  | `created_at` | `timestamptz` | время создания записи |
|  | `updated_at` | `timestamptz` | время последнего изменения |

`commercial_roles` содержит три согласованных значения: производитель, дистрибьютор и подрядчик.

`offer_types` содержит шесть согласованных категорий:

1. Материалы и строительная продукция.
2. Оборудование, техника и автопарк.
3. Строительные и монтажные работы.
4. Проектирование, изыскания и технические услуги.
5. Энергетические, коммунальные и экологические услуги.
6. Поставка, логистика, аренда и эксплуатация.

Состав `business_segments` будет наполняться отдельно и не влияет на структуру таблицы.

## Связи и кардинальности

- `okveds.parent_code → okveds.code`: одна родительская запись может иметь ноль или много дочерних.
- `company_okveds.code → okveds.code`: одному коду соответствуют ноль или много компаний; каждая запись `company_okveds` ссылается ровно на один код.
- `okveds.business_segment_code → business_segments.code`: один сегмент может использоваться многими кодами; у кода максимум один сегмент.
- `okveds.commercial_role_code → commercial_roles.code`: одна роль может использоваться многими кодами; у кода максимум одна роль.
- `okveds.offer_type_code → offer_types.code`: один тип предложения может использоваться многими кодами; у кода максимум один тип.

## Восстановление полных кодов

1. Исходные значения читаются как строки; преобразование в числовой тип запрещено.
2. Коды с потерянными завершающими нулями восстанавливаются по официальному классификатору ОКВЭД-2 с проверкой раздела и наименования. Простое дописывание нулей не допускается.
3. Если строка однозначно не сопоставляется официальному коду, она отклоняется в отчёт импорта и не записывается в `okveds`.
4. После восстановления код проверяется на уникальность, допустимую длину и существование родителя.
5. Технические дубли объединяются только при совпадении канонического кода и нормализованного наименования. Конфликтующие наименования требуют ручного решения.

## Проверка

1. Все значения `okveds.code` являются строками и сохраняют завершающие нули.
2. Для каждого ненулевого `parent_code` существует запись `okveds.code`.
3. В иерархии отсутствуют циклы.
4. `level` согласован с положением записи в дереве.
5. Каждый аналитический FK равен `NULL` или ссылается на существующее значение своего справочника.
6. Для одного кода невозможно сохранить несколько значений одного аналитического измерения.
7. `company_okveds.code` не принимает значение, отсутствующее в `okveds`.
8. Отчёт восстановления отдельно показывает исходное значение, канонический код, результат сопоставления и причину отклонения.

## Изменение ER-диаграммы

На существующей FigJam-доске нужно:

- добавить таблицы `okveds`, `business_segments`, `commercial_roles` и `offer_types`;
- добавить самоссылочную связь `okveds` для иерархии;
- связать три аналитических справочника с `okveds`;
- связать `okveds` с `company_okveds`;
- изменить ключ поля `company_okveds.code` с `PK` на `PK,FK`;
- сохранить принятый порядок столбцов: тип ключа, название поля, тип данных, комментарий.
