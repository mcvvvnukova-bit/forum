# Проверка применимости внешней идентификации

Дата проверки: 2026-08-16. Область — только автоматическое создание учётной записи и первого администратора организации для инвариантов ADR-0005. Этот документ не изменяет ADR-0005 и не устанавливает юридические полномочия пользователя.

## Вывод

Сбер ID достаточен для привязки платформенного пользователя к физическому лицу, но в рассмотренной официальной документации не предоставляет подтверждённой связи с организацией или полномочия её администратора. Его нельзя применять для bootstrap первого администратора организации.

Контур.Диадок технически предоставляет более узкое, но проверяемое основание: после OIDC-авторизации пользователь выбирает организацию и ящик из `GetMyOrganizations?autoRegister=false`; платформа запрашивает `GetMyEmployee` для этого `boxId` и принимает bootstrap только при `Permissions.IsAdministrator = true` и при **явно полученном** `AuthorizationPermission.IsBlocked = false`. Это подтверждает, что пользователь — неблокированный администратор *ящика Диадока*, а не законный представитель и не обладатель права подписи.

Следовательно, автоматический bootstrap через Диадок допустим лишь после явного продуктового решения: «администрирование выбранного ящика Диадока является достаточной authority для назначения первого администратора организации на платформе». До этого решения или подтверждения capability/prerequisites Unit 1 не должен продолжаться.

## Подтверждённые возможности

### Сбер ID

- `openid` обязателен и даёт неизменный уникальный `sub`; `email`, телефон, ФИО и расширенные персональные данные зависят от выданных системе scopes.
- Подключение требует регистрации организации и приложения, принятия оферты через ЭДО, `Client ID`, `Client Secret` и сертификата. Серверный flow включает проверку `state`, `nonce`, получение токенов и идентификацию по `sub`.
- В опубликованном списке данных отсутствуют идентификатор юридического лица, ящик ЭДО, признак членства, роль администратора, право подписи либо законное представительство. `place_of_work` — только название места работы, поэтому не является доказательством membership или authority.

Итог: создавать физическое лицо можно после корректной серверной проверки OIDC; создавать организацию или первого администратора по Сбер ID нельзя.

### Контур.Диадок

- OIDC рекомендован Диадоком. Для серверного приложения документирован Authorization Code Flow, в котором пользователь выдаёт разрешения, приложение получает `access_token`, затем использует его как `Authorization: Bearer ...` для API.
- `GetMyOrganizations` возвращает организации, к которым у пользователя есть доступ, и их ящики. В ответе приведены `Inn`, `Kpp`, `Ogrn`, `OrganizationType`, `IsActive`, `IsEmployee`, `Boxes[].BoxIdGuid` и другие сведения. По умолчанию этот вызов имеет `autoRegister=true` и при заданных условиях может зарегистрировать пользователя и назначить его администратором ящика. Поэтому для платформенного чтения списка обязателен явный параметр `autoRegister=false`: иначе Диадок может сам создать предпосылку, которую платформа затем ошибочно использует как authority. Платформа обязана позволить пользователю выбрать ровно один ящик для bootstrap, а не выводить authority из email, ИНН без ящика или произвольной организации списка.
- `GetMyEmployee?boxId=...` возвращает сведения о сотруднике, от имени которого сделан вызов, включая `Permissions`. `EmployeePermissions.IsAdministrator` означает, что сотрудник может редактировать структуру и реквизиты организации и добавлять/редактировать других сотрудников. `AuthorizationPermission` описывает ограничение доступа; пример успешного ответа показывает `IsBlocked: false`. Поскольку поле optional, отсутствующее поле, `IsBlocked = true` и неизвестная семантика — отказ (fail closed), пока официальный контракт не подтвердит эквивалентное безопасное правило. Вызов также может вернуть `403`, если доступ к ящику по токену запрещён.
- Документация называет `GetMyEmployee.User.UserId`, но не устанавливает его как стабильный канонический subject в namespace, пригодном для постоянного identity linking. До sandbox/contract-подтверждения это prerequisite; временный `access_token` не должен использоваться как внешний идентификатор, ключ аудита или доказательство authority.

## Минимальный технический поток Диадока

1. Начать серверный OIDC Authorization Code Flow с scopes `openid profile email Diadoc.PublicAPI` (в staging — соответствующий staging scope); сгенерировать и проверить `state` и `nonce`.
2. Получить токен и на сервере вызвать только `GetMyOrganizations?autoRegister=false`; показать только возвращённые организации и ящики. Пользователь выбирает один `boxId`. Нельзя вызывать endpoint без этого явного параметра: его default `true` способен зарегистрировать пользователя и назначить его администратором ящика.
3. Вызвать `GetMyEmployee` с выбранным `boxId`. Продолжить только когда запрос успешен, сотрудник зарегистрирован, `Permissions.IsAdministrator = true` и в ответе **явно есть** `AuthorizationPermission.IsBlocked = false`. Отсутствующее optional-поле, `true`, ошибка или неясная семантика означают отказ. Неявное разрешение запрещено, пока официальный контракт не подтвердит эквивалентное безопасное правило.
4. В одной идемпотентной операции создать/сопоставить организацию по подтверждённым идентификаторам Диадока и назначить первого платформенного администратора. В аудит записать provider, фактически возвращённый `GetMyEmployee.User.UserId`, `OrgIdGuid`, `boxId`, время и результаты проверок. До подтверждения стабильности/namespace `UserId` не использовать его как канонический ключ identity linking; не хранить access/refresh token как идентификатор или доказательство authority.
5. После bootstrap дальнейшее управление ролями выполняется правилами платформы. Повторная авторизация и проверка Диадока нужны для начального решения и для явно определённых операций повторной валидации, но не превращают Диадок в доказательство юридического представительства.

## Decision gate D0: критерий первого администратора

Владелец продукта и юридическая функция должны письменно утвердить или отклонить критерий:

> Для первого администратора организации FORUM достаточно того, что текущий пользователь является неблокированным администратором выбранного ящика Контур.Диадока, подтверждённым `GetMyEmployee`.

Если критерий утверждён, Диадок является выбранным техническим источником authority только в этом значении. Он **не** означает, что платформа проверила право подписи, КЭП, МЧД, сведения ЕГРЮЛ о руководителе или иной титул законного представителя.

Если критерий не утверждён, capability не подтверждена или prerequisites не выполнены, блокируется весь Unit 1, а не только обработчик первого администратора. Без нового решения нельзя заменять authority email-совпадением, одним ИНН, доступом к ящику без `IsAdministrator` или ручной модерацией.

### Ветки fallback без выбора

При отклонённом D0 допустимы только следующие альтернативы, каждая после отдельного product/legal/ADR gate; этот Unit не выбирает ни одну из них:

- КЭП/МЧД как отдельный доверенный источник authority;
- invitation/bootstrap authority model, в котором initial authority заранее определена утверждённым правилом;
- сужение provider scope до сценариев, не требующих автоматического назначения первого администратора;
- пересмотр acceptance criterion автоматического первого администратора.

Ни одна ветка не восстанавливает ручную модерацию регистрации. До одобрения ветки Unit 1 остаётся заблокированным.

## Prerequisites и неизвестные договорные условия

- Сбер ID: нужны регистрация на портале, оферта через ЭДО, credentials и сертификат. Объём фактически выданных scopes меньше максимального набора может отличаться; он должен быть подтверждён до реализации. Коммерческие, договорные и sandbox-детали в открытых источниках не подтверждены.
- Диадок: для OIDC требуется заявка на интеграцию, `client_id` и выпуск `client_secret` в Кабинете интегратора. Для работы нужны нужные scopes, зарегистрированный `redirect_uri` и доступ к Public API; `GetMyEmployee` может вернуть `402`, если у ящика нет API-подписки. Условия доступа к API, разрешение на рассматриваемый способ использования, каноничность/стабильность/namespace `GetMyEmployee.User.UserId` и точное поведение optional `AuthorizationPermission` нужно подтвердить договором и sandbox-тестом. Эти закрытые детали — prerequisite / не подтверждено.
- Нужны отрицательные sandbox-сценарии: вызов `GetMyOrganizations?autoRegister=false` не изменяет членство/права и не создаёт администратора ящика; запрос без параметра не используется в платформенном flow; выбран не тот ящик; `IsAdministrator = false`; отсутствует `AuthorizationPermission`; `IsBlocked = true`; API запрещён (`403`); нет API-подписки (`402`); token/nonce/state недействительны; повторный callback. До документированного подтверждения запрета побочного эффекта и этих сценариев capability не подтверждена, а Unit 1 остаётся заблокированным.

## Решение для следующего Unit

| Условие | Разрешение Unit 1 |
| --- | --- |
| D0 утверждён, OIDC/API-доступ, stable subject prerequisite и sandbox-проверки подтверждены | Можно начать Unit 1 и проектировать контракт bootstrap Диадока с fail-closed проверками выбранного ящика. |
| D0 не утверждён, capability либо prerequisite не подтверждён | Unit 1 не начинается; зафиксировать блокировку и запросить product/legal/ADR решение. |
| Нужна юридическая authority, а не platform authority | Данная интеграция недостаточна; требуется отдельное решение вне Unit 0. |
