# ОКВЭД2: официальный API ФНС, локальный запуск

Требования и описание: [ADM.02.02.01](https://docs.astforum.ru/doc/adm020201-integraciya-s-sistemoj-istochnikom-nJBdiTMnBK).
Задачи: [PROJ-172](https://roadmap.astforum.ru/work_packages/PROJ-172), [PROJ-22](https://roadmap.astforum.ru/work_packages/PROJ-22).

## Архитектура и контракт

Отдельный worker на Node 24 использует pg-boss 12.37.1 и PostgreSQL. Адаптер ФНС обращается к двум фиксированным HTTPS-адресам `/reference/okveds` и `/reference/groups`, проверяет JSON, лимит 8 MiB на ответ, общий таймаут 45 секунд, уникальность, иерархию и количество доступных для выбора кодов раздела. Дополнительные поля источника не переносятся. Все коды, включая родительские, сохраняются; `size` относится к `selectable=true`.

Расписание `0 1 * * 6`, `Europe/Moscow`: суббота 01:00. pg-boss сохраняет расписание, повторяет ошибку до трех раз с задержкой от 60 до 600 секунд и выполняет один пропущенный запуск после простоя (`missed: once`). Для расписания должен работать хотя бы один worker. При первом старте пустого справочника ставится начальный импорт.

SHA-256 вычисляется по отсортированным полям контракта. `unchanged` не изменяет строки или редакцию. Проверка администратора требуется при исчезновении кода/раздела, изменении иерархии, возврате неактивного кода или изменении более 10% кодов. В остальных случаях публикация автоматическая. Сравнение первой версии с уже существующим справочником также обязательно. Даты получения и публикации не являются юридическими датами вступления кодов в силу: API этих дат не предоставляет.

Прикладной сервис владеет `public.okveds`, `okved_groups`, `okved_reference_state`, `okved_imports`. Существующие внутренние классификации не входят в UPDATE. Исчезнувшие коды получают `is_active=false`; строки и внешние ключи сохраняются. Для новых выборов потребители используют `WHERE is_active AND selectable`; исторические ссылки читаются без этого фильтра. Публикация атомарна, revision и исходный хэш защищают принятие от устаревших снимков. Session advisory lock сериализует загрузку и решение; требуется прямое соединение PostgreSQL или session pooling, transaction pooling непригоден.

Собственная миграционная цепочка `migrations/references/001_okved_fns.sql` расширяет bootstrap-таблицу и создает отсутствующие справочники внутренних классификаций. Перед ней обязательны основные миграции с маркером `003_public_schema`. pg-boss использует отдельную схему `forum_reference_jobs`; миграции и создание очереди выполняются только командой `references migrate`, worker запускается с `migrate:false`. SQL попадает в образ через существующую копию каталога `migrations`.

## Локальный стенд Docker

Из корня отдельной рабочей копии:

```sh
bash scripts/deployment/build-reference-local.sh
docker compose -f deployment/local/okved.compose.yml up --no-build -d
docker compose -f deployment/local/okved.compose.yml logs worker
docker compose -f deployment/local/okved.compose.yml exec worker node dist/reference-cli.js list
```

Скрипт передает ограниченный контекст через stdin из каталога с ASCII-путем: это устраняет отказ BuildKit при кириллице в пути рабочей копии и исключает локальные секреты. Стенд использует отдельную локальную базу на `127.0.0.1:55476`, собственный volume и локальные демонстрационные учетные данные. Начальный импорт выполняется после запуска worker. Контейнер продолжает еженедельные проверки, пока компьютер и Docker работают. Остановка сохраняет данные:

```sh
docker compose -f deployment/local/okved.compose.yml down
```

## Запуск без контейнера приложения

Из `apps/api`, с `DATABASE_URL_FILE` или `DATABASE_URL`, направленным на локальную базу:

```sh
npm run build
npm run migrate
npm run references -- migrate
npm run references -- preview
npm run references -- sync
npm run worker:references
```

`preview` проверяет живой источник без записи в БД. `sync` выполняет однократный импорт. `list` выводит последние 50 попыток, `show ID` — разницу с прежними значениями и причины проверки.

## Решение администратора

CLI выполняется в доверенном служебном окружении с доступом к БД; публичные HTTP-методы и интерфейс администратора в эту задачу не входят. Оператор изучает разницу и подтверждает конкретный SHA-256:

```sh
npm run references -- show 12
npm run references -- approve 12 EXPECTED_SHA256 admin:8
npm run references -- reject 12 EXPECTED_SHA256 admin:8 "Причина отклонения"
```

Вместо `12` и `EXPECTED_SHA256` используются идентификатор и хэш из журнала. Идентификатор оператора — явная аудиторская отметка, не заменяющая IAM-аутентификацию. Для внешнего развертывания нужны отдельные роли мигратора, worker и оператора, проверенные ACL и привязка будущего интерфейса к `platform_admin`. Локальный compose использует владельца отдельной базы. Он не является конфигурацией production.

`pending_review` не меняет опубликованные данные; повторный такой снимок возвращает ссылку на исходного кандидата. Повторное отклоненное содержимое не публикуется автоматически: при изменении базовой редакции требуется новая проверка. Новый проверенный снимок источника переводит отличающиеся ожидающие версии в `superseded`, включая возврат ФНС к уже опубликованному содержимому. Решение при несовпадении хэша, редакции или фактических исходных данных запрещено. Сетевые и SQL-ошибки записываются без секретов; старый справочник остается действующим.

## Проверка

```sh
npm run typecheck --workspace apps/api
npm run build --workspace apps/api
TEST_DATABASE_CONTAINER=YOUR_DISPOSABLE_CONTAINER TEST_DATABASE_URL=YOUR_LOCAL_TEST_URL npm test --workspace apps/api
```

Тестовый URL обязан указывать на loopback, имя базы с суффиксом `_test`, без query/fragment. Тестам справочника нужна роль с `CREATEDB`: они создают и удаляют отдельные базы, чтобы не вмешиваться в деструктивные IAM-тесты.

Проверки покрывают канонизацию, неполный ответ, сохранение связей и внутренних полей, карантин и ручное решение, повторный импорт, устаревшую версию, сетевой отказ, откат SQL, параллельный импорт, реальную очередь и московское расписание.
