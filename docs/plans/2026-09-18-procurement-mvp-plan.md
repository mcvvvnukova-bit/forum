## Последовательность подготовки реализации

Календарные даты разработки не назначены: неизвестны доступная команда, готовность существующих модулей и оценки. Этапы обозначают порядок зависимостей.

| Этап | Состав | Ответственный по роли | Проверяемый результат |
|---|---|---|---|
| A. Подготовить основания | PRE-01–03, DOC-01; решения D01–D04 | Владелец продукта, аналитик, операционный руководитель | Утверждены роли, стартовая категория, исходные файлы, шаблоны и правила доступа |
| B. Превратить смету в проверенный лот | M04-F01–02, M05-F01–02, OPS-02 | Заказчик пилота, аналитик, дизайнер, команда разработки | Заказчик загружает реальную смету, исправляет неоднозначность; модератор проверяет лот |
| C. Дать доступ подходящим исполнителям | M05-F03, M06-F01–03, OPS-05 | Команда разработки, операционный владелец | Подходящие видят лот; неподходящие не видят даже по прямой ссылке; уведомления отслеживаются |
| D. Получить окончательные предложения | M07-F01–03, OPS-01 | Аналитик, дизайнер, команда разработки, исполнители пилота | Вопросы приватны; предложение принято ровно один раз; соблюдены срок и права |
| E. Завершить цикл | M08-F01–04, M09-F01, OPS-03–04 | Заказчик пилота, команда разработки и QA | Выбор закрывает приём; контакты и пакет доступны только по установленным правилам |
| F. Проверить пилот | Полный цикл и исключения | Владелец продукта, QA, поддержка | Зафиксированы результаты сценариев и исходные значения метрик; принято решение о расширении |

Аудит, разграничение доступа, адаптивность и обработка ошибок включаются в каждый этап. Подключение внешних провайдеров может идти параллельно детализации заказов; публикация зависит от готовности модерации и правил аудитории.

## Контракты и проверки перед первой вертикальной реализацией

- [ ] Подтвердить PRE-01/PRE-02: principal,participant,организационные права и обязательные документы проверяются отдельно; matching email не становится authority.
- [ ] Детализировать M04 import errors/повторный файл/нормализацию неоднозначных строк до выбора импортного формата.
- [ ] Согласовать единую таблицу lot states/versions: модерация одобренной версии, публикация, повторная модерация изменений, deadline/early-close/cancel/no-offer.
- [ ] Определить атомарную уникальность participant+lot при финальной отправке Offer и конфликт конкурентной подачи; acceptance criteria брать из исходной карточки, не добавлять draft/edit/withdraw.
- [ ] Согласовать LotVisibility и минимум раскрытия, аудит изменения доступа и уведомления at-least-once с retry/idempotency.
- [ ] Зафиксировать participant/user-author на изменениях и проверках ContactDisclosure/DealPackage; экспорт и вложения подчиняются тем же правам.
- [ ] После согласования протоколов описать success/error/authorization/state/race проверки для каждого slice и только затем оценивать реализацию.

## Проверка готовности

- [ ] Каждое открытое решение из gate выше имеет утверждённый ответ/роль владельца и версию источника.
- [ ] Definition of ready не смешивается со статусом реализации.
- [ ] Технический план первого slice ссылается на конкретные контрактные документы и разрешённую задачу; данный checklist не является разрешением на deploy.
