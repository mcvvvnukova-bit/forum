# PROJ-180: первый пакет проверки организаций до доступа Контура

Источник: `docs/plans/2026-10-11-001-feat-diadoc-organization-verification-plan.md` и поручение владельца начать первый пакет (модель → API → UI → имитатор и тесты).

Исполняется на `origin/main` 5937f25d. Исходный план сохраняется без изменений. Задача: https://roadmap.astforum.ru/work_packages/PROJ-180, родитель PROJ-5.

## Границы пакета

Подготовить additive-хранилище проверок, собственный API, интерфейс двух путей и клиент Диадока с отдельным локальным имитатором. Никакие результаты этого пакета не выдают membership, authority, business role или юридическое разрешение. Регистрация заявления, криптографическая проверка КЭП/МЧД, OIDC-linking и настоящий вход в Контур выполняются следующими пакетами общего плана. Кнопки не изображают завершённую юридическую регистрацию.

В production функция выключена по умолчанию. Имитация располагается только в test/diagnostics, не выбирается параметром пользовательского запроса и не включается переменной окружения production. Реальный клиент вызывается только с серверным пользовательским токеном, которого пока нет; API по умолчанию возвращает необходимость подключения либо подписи. Отсутствие Диадока не блокирует независимый путь КЭП.

## Контракт

- `GET /api/me/organizations/verification/options`: собственная сессия; `{userId,enabled}`.
- `GET /api/me/organizations/verification?inn=...`: собственная сохранённая организация; `{userId,item:null|Verification}`.
- `POST /api/me/organizations/verification`: точный JSON `{inn,method:'diadoc'|'kep',requestId:UUID}`; собственная сессия и точный Origin. Повтор requestId возвращает ту же попытку; другое содержание с тем же requestId — 409. GET восстанавливает последнюю попытку; неизвестный/чужой ИНН — одинаковый 404.
- DTO: id, inn, method, status, checkedAt, expiresAt, source, reason, минимальные реквизиты/технические права. `legalPermissions` всегда `{registerCompany:false,submitTender:false}`. Никаких токенов, email, полного roster или чужих участников.
- Статусы: `checking`, `connection_required`, `signature_required`, `access_confirmed`, `access_denied`, `unavailable`, `selection_required`. Последние четыре — технический результат источника, не юридическое заключение. Несколько КПП/ящиков требуют выбора в следующем пакете, не произвольного первого ящика.

## Задачи

1. Additive-миграция `008_organization_verifications`, ограниченное хранение попыток и результатов, аудит начала/окончания, runtime grants и обратная инструкция. Тесты: сохранение/повтор/конкуренция, чужой ИНН, конфликт requestId, отсутствие новых корпоративных прав.
2. Контроллер и конфигурация feature flag; provider seam с закрытым по умолчанию источником, одноразовое выполнение, CAS завершения. Тесты через createApp: Origin/session/строгий ввод, no-store, default-off, сохранение после рестарта приложения, ошибки без утечки секретов.
3. Клиент Диадока: `GetMyOrganizations?autoRegister=false`, только явный `IsEmployee=true`, затем собственный `GetMyEmployee` по единственному проверенному ящику. Неизвестная блокировка/permission → отказ от положительного подтверждения; 401/402/403/404/409/5xx/timeout и неверные данные имеют разные технические причины. Локальный HTTP-имитатор проверяет реальные запросы клиента. Никаких записывающих методов.
4. Primer UI: раскрытие проверки своей строки, два пути, загрузка результата, повтор с тем же requestId после неопределённого ответа, отдельное техническое подтверждение и юридический допуск. Смена пользователя/закрытие панели прерывают и игнорируют старые ответы. Тесты и browser QA desktop/mobile/keyboard.
5. Шлюз с точным allowlist новых путей; локальный сквозной стенд с отдельной БД; проверки API/web/Primer/layout и итоговое независимое ревью. Коммиты, push, PR с OP#PROJ-180 и OP#PROJ-5; проверка связи в OpenProject. Публикация и merge не входят.

## Готовность и оставшиеся зависимости

Рабочая собственная часть с реальным PostgreSQL и HTTP-имитатором, сохранением/повторным чтением, изоляцией пользователей и нулевой выдачей корпоративных прав. Зафиксированы проверки и ограничения. Фикстуры не подтверждают контракт Контура: staging OIDC, побочные эффекты API, optional-поля, лицензирование, безопасная последовательность методов и все юридические источники остаются внешними зависимостями.

## Локальная проверка

Для диагностики нужна отдельная локальная PostgreSQL БД с именем, заканчивающимся на `_test`; production URL и URL с query/fragment отклоняются. В каталоге `apps/api` выполнить `npx tsc -p tsconfig.test.json`, затем `node diagnostics/verification-preview.mjs` с `TEST_DATABASE_URL` либо `TEST_DATABASE_CONFIG_FILE` (JSON с полем `url`, файл вне репозитория, mode 0600). Открыть `http://127.0.0.1:4185/__preview/login`. API слушает только loopback:4186, HTTP-имитатор — случайный loopback-порт. Ни одного запроса в реальный Диадок нет.

`?user=bob` открывает второго синтетического пользователя без добавлений. `?scenario=blocked`, `certificate_only`, `multiple`, `unknown_block`, `http402` меняют ответы имитатора для следующей проверки. Успех подписан как «Тестовые сведения», оба юридических разрешения всегда false. Сервер останавливается SIGINT/SIGTERM; пользовательские ключи и токены Контура не используются.

Откат: выключить `ORGANIZATION_VERIFICATION_ENABLED` (по умолчанию false), откатить приложение; таблицу и аудит сохранить. Удаление новой таблицы допустимо только после отдельного решения о сохранении доказательств и остановки всех обращающихся к ней версий. Для пустого локального тестового окружения обратный DDL: `DROP TABLE public.organization_verifications; DELETE FROM public.schema_migrations WHERE name='008_organization_verifications';`.

## Проверка реализации 20 октября 2026

- API: 157 тестов на отдельном PostgreSQL 17; в том числе реальные ограниченные runtime grants, конкурентный повтор, изоляция пользователей, истечение срока и отсутствие новых ролей/полномочий.
- Web: 125 тестов; композиция приложений: 44; Python-шлюз: 16. Сборка всех workspaces, typecheck, ESLint web, repository Primer и layout gates проходят.
- Независимое финальное ревью выявило три важных дефекта: избыточную блокировку SELECT под runtime-ролью, необработанное отклонение при закрытии оборванного HTTP-потока и устаревший положительный результат в открытом UI. Каждый воспроизведён регрессионным тестом до исправления; после единственного прохода исправлений тесты проходят.
- Встроенный браузер Codex, локальный HTTP-имитатор: 390/768/1280 px без переполнения страницы; восстановление сохранённого результата после reload; независимый КЭП-путь; заблокированный сотрудник; второй пользователь; фокус открытия/закрытия и клавиатурный запуск. Найденное переполнение кнопок устранено штатным `Stack wrap` Primer. Ошибок console error не зарегистрировано.
- Generic Primer validator проходит в `apps/web` с предупреждениями при явном указании трёх существующих token bridge из `APPROVED_PATHS` repository gate (включая Sber). Без этого указания он сообщает о трёх существующих цветах Sber. Запуск этого валидатора в корне monorepo считает root package приложением и сообщает об отсутствующих root-зависимостях Primer; профильный repository gate проходит. Новых брендовых переменных нет; актуальные значения Forum / Light в Figma отдельно не сверялись.
- Отдельные ACL/configure-role проверки: 15/15 на PostgreSQL 18.6; добавлена проверка миграции 008 до изменения ролей и конфигурации. Primer negative regressions: 25/25. Целостность исходников и CI: 252/252; Python local-CI: 22/22; operational gate проходит. Обновлены только текущие фикстуры/контрольный снимок; исторические ownership receipts сохранены, новая ограниченная запись PROJ-180 подтверждает изменённые исходники.
- Реальные OIDC/API Контура, КЭП/МЧД, тарифы и юридический допуск этим прогоном не подтверждены. В dev/production ничего не публиковалось.

## Решения при исполнении

- Исходный ce-plan сохранён без переделки в GitNexus schema 2; связи и исходники перепроверены на текущем main. Если интерфейсы следующих пакетов изменятся, потребуется согласовать контракт.
- В этот пакет входят модель/API/UI/HTTP-имитатор. OIDC и юридическая проверка КЭП/МЧД остаются следующими пакетами; до их реализации юридического допуска нет.
- Push и PR выполнены по обязательному порядку AGENTS без повторного запроса разрешения. Worktree сохранён для ревью; merge и публикация требуют отдельного поручения.
- Primer проверен в фактическом приложении и repository gate с существующими token bridge. Новые маппинги Forum / Light не вводились; отдельная сверка Figma остаётся необходимой при изменении брендинга.
- Для изменённых исходников добавлен ограниченный successor PROJ-180 по принятому шаблону. Исторические receipts не переписаны; риск изменения общей проверки целостности покрыт тестами отказа при подменах и полным набором проверок.
