# PROJ-161 — применение и независимая проверка

Проверено 9 октября 2026 года, 22:02–22:04 по Москве. Задача: [PROJ-161](https://roadmap.astforum.ru/work_packages/PROJ-161), изменения: [PR #32](https://github.com/mcvvvnukova-bit/forum/pull/32).

## Результат

В БД `forum` применена `006_person_memberships`. Канонические поля `persons` стали обычными колонками; устаревшие `sber_profile`, `identity_provider` и `sub` допускают NULL. Источники идентификации и снимки профилей выделены отдельно. Функция и триггеры обязательного личного участника удалены. Личная сессия получает базовую роль `individual` независимо от исполнителя. Регистрация компании, членство, административные полномочия и назначения бизнес-прав имеют отдельные состояния, основания и проверки эффективного доступа.

Применение состоялось в составе публикации зависимой [PROJ-163 / PR #33](https://github.com/mcvvvnukova-bit/forum/pull/33), в 21:41 по Москве. Опубликованный API и DEV web имеют исходный коммит `b87cfb3ac8e2bdfe0d993d7016875c2a3a6ee60d`. Подготовленная в PROJ-161 сборка `368543d5246beb5356d451c168ee3f3f300ffee2` не публиковалась повторно: свежая проверка исходного коммита DEV остановила её до любых изменений в основной БД или действующем приложении.

Проверены Git и серверные SHA-256 для 18 файлов миграции, авторизации, бизнес-доступа и соответствующих контрактов: опубликованные байты совпадают с PROJ-161. Единственное дополнительное изменение в `apps/api/src/app.ts` подключает `SettingsController`; оно принадлежит PROJ-163.

## Данные и восстановление

Перед живой миграцией сохранена приватная полная custom-format копия `forum`, globals, исходные значения колонок, владельцы и ACL. Копия успешно восстановлена в изолированной БД PostgreSQL 18.6; проверены строки, исходные значения и права. Восстановленная копия прошла миграцию и повторное применение до основной БД.

Приватная квитанция принятого релиза и журнал операции совпадают по `attemptId`. При принятии миграции подтверждены сохранение всех исходных значений колонок, владельцев/ACL, неизменность повторного применения и узкие дополнительные права runtime-роли. SHA-256 SQL миграции: `6fe84ea063406bc8ec9033a62217df98e99e84bfe9d49274cf1e1366653be6c4`.

Независимая проверка после публикации подтвердила:

- `006_person_memberships` присутствует в журнале ровно один раз.
- Исходные значения колонок восстановленной копии совпадают с сохранённым снимком; исходные владельцы/ACL основной БД сохранены.
- Все три исходные учётные записи, профиля, участника и внешние идентификаторы существуют с прежними идентификаторами и владельцами.
- В момент применения было по три `users`, `persons` и `participants`, три `identity_profiles`, ноль членств и полномочий компаний. После отдельной проверки настроек PROJ-163 наблюдается по четыре аккаунта/профиля/участника: дополнительный QA-аккаунт деактивирован, его сессии отозваны и участие выключено; аудит сохранён. В рамках PROJ-161 синтетические пользователи в основной БД не создавались.
- Живые входы могут обновлять снимки провайдера и время последней аутентификации. Сохранение значений при миграции и текущая неизменность идентификаторов проверены отдельно; текущие изменяемые профили не выдаются за замороженный снимок.

Для восстановления приложения сохранён проверенный совместимый образ `sha256:113fec5ca075218aa1d2610da43877391e0b76030da65b90d412a63e649aa4b0`, коммит `3232e0c75914d9358066e667eb5c1cfd3444b8b1`. Восстановление сохраняет добавленную схему и новые данные. Старый API PROJ-160 не поддерживает новые аккаунты без исполнителя и не является подходящим возвратом после 006.

## Независимые проверки действующего релиза

Фактически опубликованный API image ID запущен отдельно против восстановленной изолированной копии, под ограниченной `forum_app_role`. Проба подтвердила второго настроенного тестового провайдера, `participant: null`, роль `individual`, сохранение самостоятельно отредактированного канонического поля при повторном входе, отсутствие автоматически созданных бизнес-участников/членств и readiness 200. Основная БД для этой пробы не использовалась.

На действующем API readiness 200. Анонимные `/api/auth/session` и `/api/profile` возвращают 401 с `Cache-Control: no-store`. Наличие общей cookie DEV не предоставляет личную сессию. Окружение и mounts API совпадают с сохранёнными до миграции.

Опубликованный ZIP независимо скачан из GitHub Actions: его SHA-256 совпадает с квитанцией, все 50 файлов соответствуют manifest, а manifest побайтово по содержимому совпадает с действующей `.web-release.json`. По нему и предыдущему manifest проверены 50 текущих и 2 сохранённых файла: 104 успешных ответа со сравнением SHA-256 на origin шлюза и публичном HTTPS. Проверены стабильный родительский read-only mount, сохранение остальных файлов и неизменность production static. Квитанция автоматического отката веб-публикации подтверждена соответствующим `rolled-back.json`.

Во встроенном браузере Codex проверены загрузка опубликованных JS/CSS, открытие диалога Сбер ID с сообщением об автоматическом создании аккаунта, возврат гостя с `/cabinet/` на `/`, мобильная ширина без горизонтального переполнения и отсутствие ошибок console. Временный viewport сброшен. Реальный вход пользователя через Сбер ID и закрытый кабинет с его данными в этой проверке не выполнялись.

Подключение других реальных провайдеров, интерфейс управления компаниями и production-публикация не входят в эту задачу. Приватные резервные копии, конфигурация, токены и персональные данные в репозиторий не включены.
