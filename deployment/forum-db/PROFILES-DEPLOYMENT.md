> Исторический отчёт о первой выкладке. Позднее 15 сентября все прикладные объекты
> перенесены в `public` миграцией 003. Актуальные имена таблиц и точка запуска —
> в [отчёте об объединении схем](PUBLIC-DEPLOYMENT.md).

Миграции `001_sber_identity` и `002_profiles` применены к рабочей базе **forum**
15 сентября 2026 года в 14:30:01 UTC (17:30:01 МСК), одной транзакцией.
Сервер: `forum-prod`, контейнер `outline-postgres-1`, PostgreSQL 18.6,
владелец схем: `outline`. Записи обеих миграций проверены в `iam.schema_migrations`.

## Созданная структура

| Таблица | Назначение |
|---|---|
| `iam.users` | Общая учётная запись человека |
| `iam.external_identities` | Связи пользователя с идентификаторами внешних провайдеров |
| `profiles.persons` | Зарегистрированное физлицо и сведения из Сбер ID |
| `profiles.organizations` | Зарегистрированные юридические лица и ИП, идентифицированные через Диадок |
| `profiles.participants` | Участники, от имени которых выполняются действия: личный исполнитель либо заказчик/исполнитель организации |
| `profiles.participant_memberships` | Независимый доступ пользователя к каждому участнику |
| `iam.role_assignments` | Роли пользователя в конкретном участнике |

Также созданы таблицы попыток входа, сессий, аудита и outbox из миграции 001.
Справочник `public.companies` имеет отдельное назначение; в него зарегистрированные
организации автоматически не копируются. Схема `party` после переноса пустой таблицы
участников удалена без `CASCADE`.

В `persons` предусмотрены все 30 полей верхнего уровня пакетов Light, Standart,
Professional и дополнительное документированное поле `address`. Вложенные реквизиты
документов и адресов сохраняются в `jsonb`. Каталог находится в
[требованиях](../../docs/brainstorms/2026-09-14-individual-registration-requirements.md).
Backend записывает проверенный снимок в `sber_profile`; именованные колонки вычисляются
PostgreSQL как `GENERATED ALWAYS ... STORED` и отдельно не редактируются. Проверка
снимка допускает только перечисленные поля и вложенные ключи; токены и коды
авторизации в него не входят. Отсутствующее значение становится SQL `NULL`;
отсутствующая самозанятость отличается от `false`.

## Связи и ограничения

- Один `iam.users` может иметь один личный профиль исполнителя и членство в нескольких
  организационных участниках. Организация может иметь несколько пользователей.
- Физлицо может действовать от своего имени только как `provider`. Членом личного
  участника может быть только его владелец. К концу транзакции у записи `persons`
  обязательно должен существовать личный участник.
- Организация может иметь отдельного участника для роли `customer` и отдельного для
  `provider`; для одной организации и роли дубликаты запрещены.
- Назначение роли требует членства того же пользователя в том же участнике.
  Бизнес-роль назначения должна совпадать с ролью участника. `organization_admin`
  разрешён только в организации и является дополнительным управленческим назначением.
- Внешний ключ связывает `persons.sub` с идентификатором Сбер ID того же пользователя.
  Данные другого пользователя привязать нельзя. Email не используется как ключ
  автоматического объединения идентичностей.
- Отзыв членства в одной организации не меняет общую учётную запись или другие
  членства. Проверка доступа в будущем backend должна учитывать активное членство,
  состояние пользователя и участника, а также соответствующее назначение роли.
  Само наличие строки в `role_assignments` ещё не означает действующий доступ.

Создание личного участника выполняется одной транзакцией: пользователь → внешняя
идентичность → `persons` → `participants` → `participant_memberships` → назначение
роли, аудит, outbox и сессия. Даты идентификации и получения профиля передаёт backend;
миграция не подставляет вместо них время создания таблиц.

## Проверки

На изолированном PostgreSQL 18 выполнен
[SQL-сценарий](tests/profiles.sql) с синтетическими данными и завершающим `ROLLBACK`:
все поля и вложенные значения, ведущие нули, форматы даты рождения, пропуски,
три состояния самозанятости, принадлежность Сбер ID, запрет личной роли заказчика,
несколько организаций и пользователей, роли и независимый отзыв членства.
Сценарий выполнен также с правами `forum_app_role`. До миграции 002 проверка
ожидаемо завершилась ошибкой отсутствия `persons`.

Проверены повторный запуск миграций без повторного создания объектов и полный
откат DDL-транзакции. На рабочем сервере проверены таблицы, внешние ключи, вычисляемые
колонки и права. Новые таблицы пользователей и профилей пусты; тестовые записи
в рабочую базу не переносились. Прежние девять таблиц `public`, их определения и
количество строк не изменились. Схемы, журнал миграций и число пользователей
`forum_sber_sandbox` сохранились; развёрнутый dev API имеет статус `healthy`.

`forum_app_role` получил необходимые права на работу с новыми таблицами и функциями,
без создания объектов в `profiles` и удаления строк `persons`. Роль
`forum_sber_sandbox_app` не получила доступ к схеме `profiles` основной базы.

## Резервная копия и запуск

До изменения создана резервная копия в закрытом каталоге сервера:

`/opt/backups/forum-profiles/20260915T142923Z/forum.dump`

SHA-256: `ec2d924dc6bd71854e44947aea5eb99558cf0c7a9931e7969353901b26d79762`.
Копия успешно восстановлена в отдельную тестовую базу, количество строк исходных
таблиц совпало. Рядом сохранены определения `public` и результаты сравнения.

Применённый комплект и журнал:
`/opt/forum-db/releases/20260915-profiles/`, `apply.log`.
Повторяемая точка входа — [apply-profiles.psql](apply-profiles.psql):

```sh
psql -X -v ON_ERROR_STOP=1 -d forum -f deployment/forum-db/apply-profiles.psql
```

Запускать из совместимого окружения от владельца схем. Скрипт использует журнал
миграций, транзакцию и блокировку мигратора. Первичное применение 002 рассчитано
на пустые таблицы идентификации: заполненная установка требует отдельного переноса
данных. Автоматический разрушительный откат после регистрации пользователей
не предусмотрен; восстановление выполняется отдельно с остановкой записей.

## Граница выполненной работы

Создана структура БД. Регистрация через Сбер ID, привязка Диадока, приглашения и
переключение участника ещё не подключены к новой модели.

Текущий `apps/api/src/migrate.ts` запускает только 001; для этой выкладки использован
отдельный psql-скрипт. Текущий `AuthStore` обращается к `party.participants` и не
совместим с новой основной схемой. Развёрнутый API продолжает использовать отдельную
`forum_sber_sandbox`, где миграция 002 не применялась. Перед подключением backend
к основной `forum` нужно обновить запросы, транзакцию регистрации, обработку полного
профиля и проверки доступа. Смена строки подключения сама по себе недостаточна.
Настройки провайдеров и работающий API этой выкладкой не изменялись.
