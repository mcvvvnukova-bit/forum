## Обязательный порядок работы с изменениями кода

Все изменения в коде этого проекта должны быть оформлены коммитами, отправлены в GitHub и включены в pull request, связанный с задачами OpenProject.

- Репозиторий: https://github.com/mcvvvnukova-bit/forum.
- OpenProject: https://roadmap.astforum.ru; проект АСТ «Форум», идентификатор `PROJ`.

### До изменения кода

1. Определить соответствующую задачу OpenProject и проверить её реальный идентификатор вида `PROJ-148`. Если подходящей задачи нет, создать её. Не использовать выдуманные идентификаторы.
2. Работать в отдельной ветке. По умолчанию использовать имя `codex/PROJ-148-краткое-описание`, подставляя идентификатор своей задачи. Если пользователь указал другое имя или требуется продолжить существующую ветку, следовать этому указанию.

### После изменения кода

1. Выполнить проверки, соответствующие изменению.
2. Оформить изменения коммитами с идентификатором задачи в сообщении. Включать только изменения текущей задачи; не добавлять посторонние правки из рабочего дерева.
3. Отправить ветку и все относящиеся к работе коммиты в репозиторий GitHub.
4. Создать pull request либо обновить существующий PR этой задачи. При необходимости использовать draft PR, чтобы результат был доступен для просмотра до окончательного ревью.
5. В описании PR указать ссылку на каждую относящуюся к изменению задачу OpenProject или её код с префиксом `OP#`, например `OP#PROJ-148`. Не ограничиваться кодом в имени ветки, заголовке PR или сообщении коммита: штатная интеграция связывает задачи по описанию PR или комментарию к нему.
6. Если PR должен отображаться также у родительской фичи, эпика или другого родительского пакета работ, явно добавить его код в описание PR. Родитель не собирает PR дочерних задач автоматически.
7. Проверить, что нужные коммиты появились в GitHub, PR содержит ожидаемые изменения, а во вкладке **GitHub** соответствующих задач OpenProject отображается этот PR.
8. При работе в Codex прикрепить созданный или обновляемый PR к текущему чату через `attach_artifact`.

### Завершение работы

Не считать работу завершённой только после локального изменения кода: обязательны коммиты, push, PR и проверенная связь с задачами OpenProject.

В итоговом ответе указать ссылки на PR и задачи OpenProject. Если какой-либо обязательный этап заблокирован отсутствием доступа или другой конкретной причиной, явно сообщить, что осталось невыполненным, и сохранить подготовленные изменения.

## Использование GitNexus

При изучении архитектуры, изменении поведения кода, отладке, рефакторинге и ревью:

1. Выбрать и прочитать подходящий встроенный skill GitNexus.
2. Прочитать контекст нужного репозитория; проверить актуальность индекса и соответствие ветки анализируемому коду.
3. Для понимания связей использовать `query`, `context` и `trace`.
4. Перед изменениями оценить последствия через `impact`; для API использовать `api_impact`.
5. После правок выполнить `detect_changes` и необходимые тесты.
6. Если GitNexus недоступен или данных недостаточно, сообщить об этом и продолжить анализ исходников обычными инструментами.
